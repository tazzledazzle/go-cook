<objective>
Harden the walking skeleton into a foundation later phases can trust: prove the store survives reopen, prove the
FTS5 triggers actually keep the search index in sync, lock down filesystem permissions and failure exit codes,
and make `-race` plus lint automatic on every commit.

Purpose: plan 01-01 makes the skeleton *work*; this plan makes the guarantees Phases 2–5 depend on *provable*.
Phase 5's SRCH-03 ("search reflects generate/publish updates with no manual reindex step") is only true if the
triggers installed in 01-01 genuinely fire — that is unverified until this plan runs. Likewise the security
posture (0700 store dir, parameterized SQL, non-zero exit on failure) is asserted in code but not yet locked by
a regression test, and PLAT-03's race-detector mandate lapses the first time someone runs plain `go test`.

Output: four new test files covering durability/index-sync/permissions/failure paths, whatever production fixes
those tests demand, and a lint + CI harness that keeps the mandate enforced.

**All paths are relative to `nerv-ecosystem/` (the Go module root and working directory), except the CI workflow,
which must live at the repository root (`../.github/workflows/`) because GitHub Actions only reads workflows from
there.**
</objective>

correct across repeated runs, **so that** I can build generate/publish/deps/search on it without re-verifying the
foundation every phase.
</phase_goal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → CLI process | `--store-path` and `MODULAR_HOME` cross here; developer-supplied, still normalized before use |
| CLI process → local filesystem | Store directory/file creation and permission bits |
| CLI process → SQLite engine | FTS5 `MATCH` terms and migration state queries cross here at runtime |
| CI runner → module source | Automated enforcement of the race/lint mandate on every push |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-01 | Tampering | runtime SQL in `internal/store` (FTS5 `MATCH` term, migration version lookups) | mitigate | Every runtime value bound with `?`, including the MATCH term; Task 1 acceptance criterion fails the task if a literal term is inlined into the query string. `gosec` in Task 3 keeps watching for string-built SQL |
| T-1-02 | Information Disclosure | store directory and database file permissions | mitigate | Task 2 asserts the directory is exactly 0700 and the database file carries no group/other bits, converting wave 1's implementation detail into a regression lock |
| T-1-03 | Tampering / Denial of Service | silent WAL-mode failure | mitigate | Task 1's WAL multi-reader case fails if the store silently fell back to rollback-journal mode, adding a behavioral check on top of wave 1's pragma assertion |
| T-1-05 | Repudiation | failed invocation reported as success | mitigate | Task 2 asserts the root command returns a non-nil error and the built binary exits 1 for an unopenable store; without this, Cobra's own error printing makes a missing `os.Exit(1)` invisible while scripts and CI read success (RESEARCH Pitfall 5) |
| T-1-06 | Tampering | corrupted FTS5 external-content index from an incorrect delete path | mitigate | Task 1 requires the `('delete', ...)` special-insert trigger form and proves post-delete/post-update index consistency by query, not by inspection |
| T-1-07 | Elevation of Privilege | unreviewed lint suppression hiding a `gosec` finding | accept | Single-operator repository with no external contributors; controlled by the Task 3 criterion that any `nolint` carry an inline reason, rather than by a tooling gate |

No new third-party packages are installed by this plan, so no package-legitimacy checkpoint applies
(`golangci-lint` and the GitHub Action are tooling, not module dependencies).
</threat_model>
