<objective>
Deliver the Nerv Ecosystem walking skeleton: one Go binary whose `modular status` command opens (creating
if needed) a single embedded SQLite store in WAL mode with the FTS5 search table live, proven end-to-end by
table-driven tests written before the production code.

Purpose: PLAT-01, PLAT-02, and PLAT-03 are the foundation every later phase stands on. Phases 2–5 add domain
packages that reach the database only through `internal/store`; if the store's WAL pragma or FTS5 bootstrap is
silently wrong (RESEARCH Pitfall 1 — modernc ignores the mattn-style DSN with no error), every later slice
inherits a broken foundation. This plan makes that foundation observable from a shell and locked by tests.

Output: `go.mod` with pinned dependencies, `internal/store` (sole owner of `database/sql`), `cmd/` (Cobra
wiring only), `main.go`, and a green `go test ./... -race -count=1`.

**All paths in this plan are relative to `nerv-ecosystem/` — the Go module root and the working directory for
every command below.** Architectural decisions are fixed by `01-SKELETON.md`; do not renegotiate them here.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → CLI process | Developer-supplied flags (`--store-path`) and environment (`MODULAR_HOME`) enter the process here. Trusted-but-fallible input: this is a single-operator local CLI, not a network service |
| CLI process → local filesystem | Store directory and SQLite files are created here; permissions and path resolution matter |
| CLI process → SQLite engine | Every SQL statement crosses this boundary; static embedded migrations vs. runtime parameterized queries |
| build → module dependency graph | `go get` pulls third-party code into the binary (supply chain) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-01 | Tampering | `internal/store` SQL surface | mitigate | All runtime queries use `?` placeholders (`HasTable`, `schema_migrations` lookups/inserts); migration SQL is static `embed.FS` content, never runtime-assembled. Enforced by Task 2 acceptance criterion grepping for `fmt.Sprintf` on lines containing SQL verbs |
| T-1-02 | Information Disclosure | store directory / database file | mitigate | `os.MkdirAll(dir, 0o700)` in `Open` before any file is created; the driver creates the database file at 0600. Mode assertions are locked by a regression test in plan 01-02 T2 |
| T-1-03 | Tampering / Denial of Service | SQLite journal mode | mitigate | Use the modernc `_pragma=journal_mode(WAL)` DSN form and assert the effective mode by reading `PRAGMA journal_mode` back in a test (Task 1 behavior, Task 2 implementation). A silently ignored pragma leaves the store in rollback-journal mode with no error, risking corruption under concurrent access |
| T-1-04 | Denial of Service | SQLite write contention | mitigate | `SetMaxOpenConns(1)` + `SetMaxIdleConns(1)` + `busy_timeout(5000)`; WAL alone does not prevent pool-level write/write contention |
| T-1-SC | Tampering | `go get` of cobra / sqlite / testify / go-cmp | mitigate | RESEARCH's Package Legitimacy Audit covers all four at pinned versions with an Approved disposition and no `[SLOP]` verdicts; the `modernc.org/sqlite` `[SUS]` flag was a slopcheck release-date/GitHub-source-only false positive, overridden with `proxy.golang.org` version-history evidence. Installs are version-pinned and `go mod verify` runs in Task 1's automated check, so no blocking human checkpoint is required |

Deferred by scope, not by omission: untrusted `--name`/`--team` path-traversal validation is GEN-07 (Phase 2);
`--store-path` cleaning is a developer-input concern handled in plan 01-02 T2.
